# Правила поведения

@memory.md

Проектная память ведётся в `memory.md` (файл подключён строкой выше). Туда записываются только устойчивые сведения, которые понадобятся в следующих чатах:
устройства и окружение, постоянные правила разработчика, технические особенности и ловушки инструментов и библиотек.
Не записывать в `memory.md`: ход обсуждения, промежуточные решения, описание реализованного (оно в `ai_map.txt`) и планируемого функционала.
Записывать один раз, когда сведение подтверждено, а не после каждого ответа.

Ничего не устанавливать и не публиковать без спроса. Ничего не меняй и не исправляй по своей инициативе. Все изменения только после получения явной команды.
Исключение — `memory.md`: его пополняй и правь без отдельной команды, соблюдая правила выше.

Не добывай самостоятельно сведения, которые можно получить вопросом: не сканируй каталоги, не запускай пробные сборки и проверочные скрипты ради уточнения предположений - спроси у разработчика.

Если при решении задачи возникают вопросы, выведи их полный список с кратким описанием (максимум 2 предложения), после чего выведи первый вопрос с конкретикой.
Переходи к следующему вопросу только после получения команды.

Все текстовые файлы проекта в кодировке UTF-8, новые файлы создавай в этой кодировке.
При создании новых файлов, если это возможно, в начале файла создавать комментарий "русский текст для того чтобы редакторы не путали кодировку".
Максимально допустимая длина строки текстовых файлов - 200 символов.

При создании кода, если требуется создать утилитарную функцию, константу или Composable оценивай, могут ли они понадобится в будущем в другом коде. Если могут, то создавай ее в каталоге "src\utils", если код уникален для 
места описания и он не используется для реализации внешних интерфейсов, помечай его комментарием "FOR LOCAL USE" и создавай комментарий с описанием назначения этого элемента.

Все комментарии в исходных файлах создавай на русском. Не создавай комментариев, описывающих поведение кода, если это поведение очевидно из самого кода, названий функций, параметров или возвращаемых типов.
Когда создаешь комментарии к классам или функцяим НЕ ПИШИ туда самоочевидные вещи, не описывай параметры смысл которых понятен из имене и типа, возвращаемые значения если они не возвращают что-то что не очевидно из описания функции.
Не создавай развернутые описание для коротких функций действие которых очевидно из тела функции только несколько слов с общим назначением и только в случае если описание не будет совпадать с именем функции.
Комментарии, кроме располоежнных внутри функций, создавай в формате:
  Если комментарий из одной троки, то пиши его в одну строку в формате /** КОММЕНТАРИЙ */ и если это объявление поля, элемента перечисления или константы располагай комментарий ПОСЛЕ объявления элемента в строке объявления.
  Если комментарий более одной строки - он располагается ПЕРЕД объявления элемента в формате:
    /** Описание1
        Описание2
        ...
    */ 

## Карта проекта для ИИ

Карта проекта — файлы `ai_map.txt`: один в корне проекта и по одному в каждом каталоге исходников.
Читай их вместо сканирования исходников: корневой индекс всегда, карту каталога — когда работаешь в этом каталоге.
Поиск по каталогу выполняй только если не нашел данных расположения нужного объекта из карт.
Формат карты — простой текст без разметки: ни звёздочек, ни обратных кавычек, ни дефисов списков. Строка вида «Имя.kt: назначение», ниже с отступом ключевые публичные элементы, ещё глубже — члены классов.
Без пересказа кода и без самоочевидного: если из имени и типа всё ясно, описание не нужно. Пустых записей «публичных элементов нет» не создавать — такой файл упоминается одной строкой.
Карта отвечает на три вопроса и ТОЛЬКО на них: 
1) где это лежит
2) что уже готово и не надо писать заново
3) что сломается снаружи, если изменить
Третье — это межфайловые связи и ловушки, не видные из того файла, который правишь: порядок регистрации, единственная точка изменения, запреты, неочевидные условия видимости.
Как устроено внутри файла — не писать: размеры, отступы, цвета, состав строки списка, формулы, порядок веток. Это читать в исходнике когда берешь файл в работу.
Исключение — `src\utils\ai_map.txt`: там сигнатуры помощников нужны целиком, по ним видно, что функция уже написана.

**Обязательно при каждом изменении исходников.** Правишь файл — тем же действием правишь `ai_map.txt` его каталога, до ответа разработчику, без отдельной команды.
Создал или удалил файл — правишь и карту каталога, и корневой индекс. Переименовал или изменил сигнатуру публичного элемента — правишь строку о нём.
Задача не считается выполненной, пока карта не соответствует коду.

При каждом исправлении приложения которое будет приводить к пересборке, после внесения изменений увеличивать значение поля "versionCode" в файле "version.properties".

Ключ подписи приложения в каталоге `appKey` публикуется намеренно: без него невозможно выпустить обновление уже установленного приложения.
